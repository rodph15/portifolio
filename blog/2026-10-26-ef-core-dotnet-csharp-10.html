EF Core em .NET 10: por que um ORM melhora segurança, desempenho e testes

Entity Framework Core não elimina a necessidade de entender SQL: ele torna o acesso a dados mais seguro, expressivo e testável quando usado com critérios claros.

ORM Segurança Testes

Em uma aplicação .NET, acessar o banco de dados com comandos SQL escritos como texto pode parecer direto no início. À medida que filtros, relacionamentos, paginação, validações e mudanças no modelo crescem, essa abordagem passa a espalhar detalhes de persistência pela aplicação. O Entity Framework Core (EF Core) é um ORM: ele mapeia classes C# para tabelas e permite expressar muitas consultas e alterações com LINQ, mantendo o SQL como responsabilidade do provedor de banco.

Instale e configure EF Core passo a passo

O exemplo abaixo usa uma Minimal API .NET 10 com SQL Server. Crie o projeto, adicione o provedor do banco e as ferramentas de migração. Em projetos reais, mantenha a versão dos pacotes EF Core alinhada à versão major do runtime usado pela aplicação.

1. Crie o projeto e instale os pacotes

dotnet new webapi --name Catalog.Api --framework net10.0
cd Catalog.Api

dotnet add package Microsoft.EntityFrameworkCore.SqlServer --version 10.*
dotnet add package Microsoft.EntityFrameworkCore.Design --version 10.*
dotnet tool install --global dotnet-ef

Em seguida, armazene a connection string em `appsettings.Development.json` para desenvolvimento local. Não coloque senhas ou outras credenciais em arquivos enviados ao repositório; em desenvolvimento, use User Secrets quando necessário e, em produção, use o mecanismo de segredos da plataforma.

2. Configure a connection string

{
  "ConnectionStrings": {
    "Catalog": "Server=(localdb)\\mssqllocaldb;Database=CatalogDb;Trusted_Connection=True;TrustServerCertificate=True"
  }
}

Defina a entidade e o contexto. `DbSet<Product>` representa a coleção de produtos consultada e alterada pela aplicação. A configuração no contexto mantém o mapeamento e as regras do banco próximos ao modelo, em vez de espalhá-los por strings SQL.

3. Crie a entidade e o contexto

using Microsoft.EntityFrameworkCore;

public sealed class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public decimal Price { get; set; }
    public bool IsActive { get; set; }
}

public sealed class CatalogDbContext(DbContextOptions<CatalogDbContext> options)
    : DbContext(options)
{
    public DbSet<Product> Products => Set<Product>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Product>(entity =>
        {
            entity.Property(product => product.Name).HasMaxLength(200);
            entity.Property(product => product.Price).HasPrecision(18, 2);
            entity.HasIndex(product => product.Name);
        });
    }
}

4. Registre o contexto, crie a migração e aplique o esquema

// Program.cs
builder.Services.AddDbContext<CatalogDbContext>(options =>
    options.UseSqlServer(
        builder.Configuration.GetConnectionString("Catalog")));

// Terminal
dotnet ef migrations add InitialCreate
dotnet ef database update

A migração é uma alteração versionada do esquema. Revise os arquivos gerados antes de aplicá-los e execute migrações no fluxo de entrega de forma controlada; iniciar a aplicação não deve ser a única estratégia para alterar um banco de produção.

Segurança: parâmetros por padrão, não por acidente

O principal risco de concatenar entrada do usuário em uma string SQL é a injeção de SQL. Uma consulta LINQ do EF Core envia valores como parâmetros; o valor do filtro não se torna parte da instrução SQL. Isso reduz uma classe importante de falhas sem exigir que cada desenvolvedor se lembre da montagem correta de parâmetros em todo ponto de acesso aos dados.

Isso não torna qualquer código seguro automaticamente. Autorização, validação de regras de negócio, menor privilégio para a conta do banco e proteção de segredos continuam indispensáveis. SQL bruto ainda pode ser a escolha certa em casos específicos, mas deve usar APIs parametrizadas, como `FromSqlInterpolated`, ou parâmetros explícitos — nunca interpolar valores não confiáveis em uma string.

EF Core também não aplica `strip tags` automaticamente. Tags HTML enviadas em campos de texto são dados e serão persistidas como foram recebidas. A defesa correta depende do uso: valide ou sanitize HTML no limite de entrada quando o produto permitir conteúdo rico, e faça encoding de saída no contexto de renderização para evitar XSS. Em uma API, isso geralmente é responsabilidade da camada que recebe ou exibe o conteúdo — não do ORM.

Um modelo coerente entre domínio e banco

Com um `DbContext`, entidades e configurações centralizadas, o modelo de dados deixa de ser repetido em dezenas de comandos, leitores de dados e mapeamentos manuais. Migrações versionam a evolução do esquema junto ao código; relacionamentos, conversões de tipos e restrições podem ser descritos de forma explícita. Isso diminui código repetitivo e torna revisões mais focadas na intenção da mudança.

Uma consulta tipada e paginada

var products = await dbContext.Products
    .AsNoTracking()
    .Where(product => product.IsActive && product.Name.Contains(searchTerm))
    .OrderBy(product => product.Name)
    .Select(product => new ProductListItem(
        product.Id,
        product.Name,
        product.Price))
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .ToListAsync(cancellationToken);

O compilador ajuda a localizar propriedades renomeadas e tipos incompatíveis antes da aplicação chegar ao banco. Isso não substitui a revisão do SQL gerado para consultas críticas, mas cria uma interface mais segura para a maior parte do trabalho diário.

Desempenho: o ORM não dispensa medir

EF Core gera SQL; ele não torna a latência do banco irrelevante. Uma consulta eficiente continua dependendo de índices adequados, filtros seletivos, paginação, projeção das colunas necessárias e um bom desenho do modelo. Para consultas somente de leitura, `AsNoTracking()` evita o custo de rastrear entidades que não serão alteradas. Projetar diretamente para um DTO também evita carregar colunas e grafos inteiros sem necessidade.

Atenção especial ao problema N+1: carregar uma lista e depois consultar uma relação para cada item pode gerar muitas viagens ao banco. Carregamento ansioso com `Include`, projeções com `Select` e consultas explícitas são ferramentas diferentes; escolha a que produz o SQL e a quantidade de dados necessários. Habilite logs em desenvolvimento, inspecione o SQL gerado e use métricas para confirmar o comportamento em cenários reais.

Há consultas analíticas, operações em massa ou recursos específicos do banco que podem justificar SQL manual, procedimentos armazenados ou uma biblioteca mais enxuta. A decisão não é ORM ou SQL: é usar a abstração certa, sem abrir mão de parâmetros, observabilidade e testes. EF Core permite combinar essas abordagens quando necessário.

Testes: dependa de uma fronteira útil

Um `DbContext` pode ser substituído ou isolado em testes de serviços que coordenam regras de negócio, e consultas podem ser verificadas contra um banco de teste. Para testes unitários, muitas equipes extraem regras que não dependem de persistência e testam-nas sem banco. Para a integração, um banco relacional efêmero — por exemplo, SQLite em memória ou um contêiner com o mesmo motor de produção — verifica tradução de LINQ, constraints e transações de forma muito mais fiel.

O provedor EF Core InMemory é útil para cenários simples, mas não se comporta como um banco relacional e pode esconder diferenças de SQL, relacionamentos e transações. Não use mocks para provar que uma consulta SQL funciona, nem use um teste de integração para cada regra pura. Separe as responsabilidades e escolha o tipo de teste que pode falhar pelo motivo certo.

ORM é uma escolha de engenharia

Usar EF Core em C# e .NET 10 não significa abandonar o conhecimento de SQL; significa tornar o caminho seguro e produtivo o padrão. Consultas parametrizadas, um modelo tipado, migrações, projeções conscientes e uma estratégia de testes reduzem riscos e custos de manutenção. Conhecer o que o ORM gera — e sair dele pontualmente quando os dados mostrarem necessidade — é o equilíbrio que transforma a abstração em vantagem.
