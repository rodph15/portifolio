SOLID em C# e .NET 10: código mais fácil de manter e revisar

Os cinco princípios não são regras para criar mais abstrações: são heurísticas para manter responsabilidades claras, mudanças locais e reviews compreensíveis — inclusive quando a primeira versão vem de uma IA.

C#ArquiteturaCode review e IA

SOLID é um conjunto de cinco princípios de design orientado a objetos. Em vez de decorar siglas, use-os para fazer uma pergunta prática durante a implementação ou revisão: este código deixa claro o que muda, quem depende de quem e qual é o menor lugar que precisa ser alterado?

Por que SOLID importa ainda mais com IA

Assistentes geram código rapidamente, mas não conhecem automaticamente as fronteiras do domínio, os riscos operacionais nem o custo de uma abstração. Princípios explícitos reduzem o espaço de interpretação: uma classe pequena é mais fácil de explicar, uma interface específica é mais fácil de testar e uma mudança localizada é mais fácil de revisar. Isso torna o diff legível para pessoas, ferramentas estáticas e a IA usada na próxima alteração.

1. SRP — Single Responsibility Principle

Uma classe deve ter uma razão principal para mudar. Não significa “uma linha por classe”; significa separar políticas que evoluem por motivos diferentes. Um handler que valida pedido, calcula preço, grava no banco e envia e-mail mistura regras e infraestrutura.

public sealed class OrderPricing
{
    public decimal Calculate(Order order) => order.Items.Sum(i => i.Price * i.Quantity);
}

public sealed class CreateOrderHandler(
    OrderPricing pricing,
    IOrderRepository repository,
    IReceiptSender receiptSender)
{
    public async Task HandleAsync(Order order, CancellationToken ct)
    {
        var total = pricing.Calculate(order);
        await repository.SaveAsync(order, total, ct);
        await receiptSender.SendAsync(order.CustomerEmail, total, ct);
    }
}

2. OCP — Open/Closed Principle

Componentes devem estar abertos para extensão e fechados para alterações recorrentes. Quando cada novo desconto exige editar um grande if, o risco cresce. Modele uma política e adicione implementações.

public interface IDiscountPolicy
{
    decimal Apply(decimal subtotal);
}

public sealed class VipDiscount : IDiscountPolicy
{
    public decimal Apply(decimal subtotal) => subtotal * 0.90m;
}

public sealed class Checkout(IReadOnlyCollection<IDiscountPolicy> policies)
{
    public decimal Total(decimal subtotal) => policies.Aggregate(subtotal, (value, p) => p.Apply(value));
}

3. LSP — Liskov Substitution Principle

Uma implementação deve poder substituir o contrato sem quebrar as expectativas do consumidor. Se uma subclasse lança NotSupportedException para uma operação prometida pela interface, a abstração está errada. Separe capacidades.

public interface IReadableDocument
{
    string Read();
}

public interface IWritableDocument
{
    void Write(string content);
}

public sealed class ReadOnlyDocument(string content) : IReadableDocument
{
    public string Read() => content;
}

4. ISP — Interface Segregation Principle

Clientes não devem depender de métodos que não usam. Interfaces menores tornam as dependências e os testes claros. Em APIs de aplicação, prefira contratos orientados ao caso de uso a uma interface “Deus”.

public interface IOrderReader
{
    Task<Order?> FindAsync(Guid id, CancellationToken ct);
}

public interface IOrderWriter
{
    Task SaveAsync(Order order, decimal total, CancellationToken ct);
}

public sealed class OrderQuery(IOrderReader reader)
{
    public Task<Order?> GetAsync(Guid id, CancellationToken ct) => reader.FindAsync(id, ct);
}

5. DIP — Dependency Inversion Principle

Módulos de alto nível devem depender de abstrações, não de detalhes. O .NET 10 facilita a composição no ponto de entrada com DI; a regra de negócio conhece o contrato e o Program.cs escolhe a infraestrutura.

public interface IClock
{
    DateTimeOffset UtcNow { get; }
}

public sealed class ExpirationService(IClock clock)
{
    public bool IsExpired(DateTimeOffset expiresAt) => expiresAt <= clock.UtcNow;
}

builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddScoped<ExpirationService>();

Como usar SOLID no code review

Não procure a sigla por si só. Pergunte: a classe tem motivos de mudança diferentes? Uma nova variação exige editar código estável? Toda implementação respeita o contrato? O consumidor precisa conhecer métodos que não usa? A regra depende de banco, relógio ou HTTP diretamente? Essas perguntas transformam SOLID em critérios objetivos para revisar código gerado por IA, em vez de uma opinião estética.

SOLID não é burocracia

Abstrações sem variação real aumentam indirection e custo cognitivo. Comece pelo comportamento, extraia fronteiras quando houver uma mudança provável ou uma necessidade de teste e mantenha o design proporcional ao problema. SOLID é uma ferramenta de comunicação e evolução, não uma obrigação de criar cinco interfaces para cada classe.

Quando aplicado com contexto, SOLID reduz alterações em cascata, melhora a testabilidade e deixa as decisões visíveis. Para equipes que usam IA, isso é especialmente valioso: quanto mais claro o design, melhor o prompt, menor o diff e mais confiável a revisão humana.
