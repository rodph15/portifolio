Middlewares no ASP.NET Core: pipelines e exemplos práticos

Uma forma previsível de concentrar preocupações transversais antes e depois de cada requisição.

.NETASP.NET CoreArquitetura

Em uma aplicação ASP.NET Core, cada requisição HTTP passa por uma sequência de componentes antes de chegar a um endpoint. Middlewares são esses componentes: código reutilizável que pode observar, alterar ou encerrar uma requisição e sua resposta. Eles evitam repetir a mesma regra em controllers e endpoints.

O que é a pipeline?

A pipeline é a ordem em que os middlewares executam. Na ida, cada componente pode trabalhar antes de chamar o próximo; na volta, ele recebe o controle novamente e pode trabalhar sobre a resposta. Um middleware também pode fazer short-circuit: devolver uma resposta sem chamar o próximo. Autenticação, autorização, CORS, arquivos estáticos, roteamento e endpoints são exemplos comuns nessa cadeia.

Request
  ↓
Exception handler → HTTPS → Routing → Authentication → Authorization → Endpoint
  ↑
Response

A ordem não é detalhe de implementação. Um handler de exceções precisa estar cedo para capturar falhas de quem vem depois. UseAuthentication precisa vir antes de UseAuthorization, e ambos antes dos endpoints protegidos. Registrar um middleware depois de MapGet ou MapControllers pode significar que ele nunca vê a requisição que você pretendia tratar.

Middlewares prontos do framework

Muitas necessidades já têm middleware no framework. O exemplo abaixo configura HTTPS, roteamento, autenticação e autorização. Cada chamada Use adiciona um componente à pipeline; MapControllers define o terminal que atende a rota correspondente.

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddAuthentication().AddJwtBearer();
builder.Services.AddAuthorization();
builder.Services.AddControllers();

var app = builder.Build();

app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();
app.MapControllers();

app.Run();

Um middleware personalizado para medir requisições

Para regras específicas da aplicação, Use aceita uma função que recebe o contexto e o próximo componente. Este exemplo mede o tempo total da requisição e inclui método, caminho e status no log. Evite registrar informações sensíveis — como tokens, senhas ou corpos completos — sem uma política clara de proteção de dados.

using System.Diagnostics;

app.Use(async (context, next) =>
{
    var stopwatch = Stopwatch.StartNew();

    await next();

    stopwatch.Stop();
    app.Logger.LogInformation(
        "{Method} {Path} responded {StatusCode} in {ElapsedMs} ms",
        context.Request.Method,
        context.Request.Path,
        context.Response.StatusCode,
        stopwatch.ElapsedMilliseconds);
});

Exemplo: handler global de erros

Tratamento global de erros é uma das aplicações mais importantes de middleware. Em vez de colocar try/catch em toda action, um único componente registra a exceção e produz uma resposta consistente. Para APIs, ProblemDetails é um formato padronizado e útil para clientes e ferramentas.

using Microsoft.AspNetCore.Diagnostics;
using Microsoft.AspNetCore.Mvc;

public sealed class GlobalExceptionHandler(
    ILogger<GlobalExceptionHandler> logger,
    IProblemDetailsService problemDetails) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(
        HttpContext context,
        Exception exception,
        CancellationToken cancellationToken)
    {
        logger.LogError(exception,
            "Unhandled exception for {Method} {Path}",
            context.Request.Method,
            context.Request.Path);

        context.Response.StatusCode = StatusCodes.Status500InternalServerError;

        await problemDetails.WriteAsync(new ProblemDetailsContext
        {
            HttpContext = context,
            Exception = exception,
            ProblemDetails = new ProblemDetails
            {
                Status = StatusCodes.Status500InternalServerError,
                Title = "An unexpected error occurred."
            }
        });

        return true;
    }
}

Registre o handler e ProblemDetails no contêiner de dependências; depois, ative o middleware uma única vez no começo da pipeline.

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler<GlobalExceptionHandler>();

var app = builder.Build();

app.UseExceptionHandler();

app.MapGet("/orders/{id:int}", (int id) =>
    id > 0 ? Results.Ok(new { id }) : throw new InvalidOperationException());

app.Run();

Essa implementação mantém o Program.cs enxuto, permite testar o handler isoladamente e centraliza a decisão sobre logs e respostas. Coloque UseExceptionHandler no início da pipeline, antes de componentes que possam lançar exceções. Em produção, não devolva stack traces, mensagens de banco de dados ou detalhes internos ao cliente. Erros previstos de validação, autorização ou recurso inexistente devem continuar retornando seus status apropriados, como 400, 401, 403 ou 404, em vez de virar 500.

Como escolher e testar a ordem

Comece pelos middlewares de infraestrutura que protegem toda a aplicação, depois aplique roteamento, identidade e autorização, e por fim endpoints. Mantenha cada middleware pequeno, com uma responsabilidade clara, e use injeção de dependência para serviços como logs ou métricas. Teste os caminhos de sucesso, o short-circuit e as falhas: a resposta deve ter status, cabeçalhos e corpo esperados, e exceções não devem vazar detalhes.

Uma pipeline bem ordenada torna as regras transversais explícitas e consistentes. Com middlewares, a aplicação pode tratar erros, segurança e observabilidade em um só lugar, deixando os endpoints concentrados no caso de uso que realmente precisam atender.
