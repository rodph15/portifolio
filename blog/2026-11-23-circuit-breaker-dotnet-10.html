Circuit Breaker em C# e .NET 10: como proteger chamadas HTTP

Quando um serviço externo falha, repetir chamadas indefinidamente pode transformar uma indisponibilidade isolada em uma falha em cascata. O Circuit Breaker interrompe temporariamente o tráfego, dá tempo para a dependência se recuperar e evita desperdiçar recursos.

.NET 10ResiliênciaHTTP

Circuit Breaker é um padrão de resiliência inspirado no disjuntor elétrico. Em vez de continuar chamando uma dependência que está falhando, o cliente abre o circuito e falha rapidamente. Isso reduz latência, pressão sobre o serviço remoto e consumo de threads, conexões e CPU.

As três fases do circuito

Um circuito começa Closed: as chamadas passam e as falhas são contabilizadas. Depois de atingir o limite configurado, ele muda para Open: novas chamadas são rejeitadas sem acessar a rede. Após uma janela de espera, entra em Half-Open para testar a recuperação; se a chamada funcionar, volta a Closed, e se falhar, retorna a Open.

Implementação recomendada para HttpClient

No .NET 10, a opção prática para uma API ASP.NET Core é registrar o cliente com Microsoft.Extensions.Http.Resilience. O handler padrão combina timeout, retry, circuit breaker e outras estratégias com configurações seguras para HTTP. Para um caso específico, customize o pipeline e defina quais erros são transitórios.

dotnet add package Microsoft.Extensions.Http.Resilience

builder.Services.AddHttpClient<PaymentsClient>(client =>
{
    client.BaseAddress = new Uri("https://payments.example.com");
})
.AddStandardResilienceHandler(options =>
{
    options.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(10);
    options.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(30);
    options.CircuitBreaker.FailureRatio = 0.5;
    options.CircuitBreaker.MinimumThroughput = 20;
    options.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(15);
});

O exemplo abre o circuito quando pelo menos 20 operações foram observadas na janela e metade delas falhou. Os valores não são universais: ajuste-os com métricas, considerando volume, latência e comportamento do fornecedor.

Entendendo a máquina de estados

Uma implementação manual ajuda a enxergar a regra, mas exige cuidar de concorrência, relógio, telemetria e sincronização. Em produção, prefira uma biblioteca mantida e testada; use o exemplo abaixo como modelo didático de decisão.

public sealed class SimpleCircuitBreaker
{
    private readonly object gate = new();
    private readonly int threshold;
    private readonly TimeSpan breakDuration;
    private int failures;
    private DateTimeOffset? openedAt;

    public SimpleCircuitBreaker(int threshold, TimeSpan breakDuration)
        => (this.threshold, this.breakDuration) = (threshold, breakDuration);

    public bool AllowRequest()
    {
        lock (gate)
        {
            if (openedAt is null) return true;
            if (DateTimeOffset.UtcNow - openedAt < breakDuration) return false;
            openedAt = null; // tentativa Half-Open simplificada
            return true;
        }
    }

    public void RecordSuccess() { lock (gate) failures = 0; }
    public void RecordFailure()
    {
        lock (gate)
        {
            if (++failures >= threshold) openedAt = DateTimeOffset.UtcNow;
        }
    }
}

Vantagens e limites

Entre os ganhos estão falha rápida, menor efeito cascata, recuperação mais previsível e uma fronteira clara para observabilidade. O Circuit Breaker não corrige a causa da falha, não substitui timeout e não deve ser usado para mascarar erros permanentes, como validação inválida ou autorização negada.

Combine-o com timeout, retry com backoff e jitter, limites de concorrência e fallback apenas quando houver uma resposta degradada correta. Não repita operações não idempotentes sem uma estratégia de idempotência. Registre mudanças de estado, rejeições, taxa de falha e duração do circuito para alertas e diagnóstico.

Circuit Breaker é uma decisão operacional

O padrão funciona quando o sistema aceita falhar de maneira controlada. Comece com o handler padrão, meça o comportamento real e customize apenas o que a dependência e o domínio exigirem. Assim, a aplicação protege seus próprios recursos sem esconder a indisponibilidade do serviço remoto.
