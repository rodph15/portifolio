Injeção de dependência no .NET 10: por que importa e como aplicar

Uma maneira de reduzir acoplamento, tornar regras explícitas e construir aplicações mais fáceis de evoluir e testar.

.NET 10ArquiteturaTestes

Injeção de dependência, ou DI, é o padrão em que uma classe recebe os serviços de que precisa em vez de criá-los internamente. No .NET 10, o contêiner nativo do ASP.NET Core resolve essas dependências e entrega a implementação configurada quando cria controllers, endpoints, hosted services e outros componentes. O resultado é uma aplicação em que as colaborações ficam visíveis no construtor.

O problema de criar dependências dentro da classe

Quando um serviço instancia diretamente um repositório, um cliente HTTP ou um relógio, ele fica preso a detalhes concretos. Trocar a infraestrutura exige alterar a regra de negócio; testar o comportamento exige banco, rede ou tempo real. DI inverte esse controle: a classe declara o contrato de que depende, e a composição da aplicação decide qual implementação usar.

public sealed class OrderService
{
    private readonly SqlOrderRepository _repository = new();

    // A regra de negócio agora conhece a infraestrutura.
}

1. Registre contratos e implementações

O ponto de composição costuma ser o Program.cs. Registre a interface, a implementação e o ciclo de vida adequado. O contêiner consegue criar a cadeia inteira se todas as dependências do construtor também estiverem registradas.

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddTransient<IEmailSender, SmtpEmailSender>();

var app = builder.Build();

Use Singleton para objetos seguros de compartilhar por toda a aplicação, como configurações imutáveis ou um cache projetado para concorrência. Scoped cria uma instância por requisição HTTP e é a escolha comum para DbContext e serviços que dependem dele. Transient cria uma instância a cada resolução e serve para componentes leves e sem estado. Um singleton não pode depender de um scoped: isso manteria uma dependência de requisição viva além do seu escopo.

2. Aplique DI à regra de negócio

A regra recebe abstrações pelo construtor e concentra-se em coordenar o caso de uso. A sintaxe de construtor primário do C# deixa isso conciso, mas o benefício é arquitetural: o serviço deixa de escolher banco, relógio e telemetria por conta própria.

public interface IOrderService
{
    Task<Order> CreateAsync(CreateOrder command, CancellationToken cancellationToken);
}

public sealed class OrderService(
    IOrderRepository repository,
    IClock clock,
    ILogger<OrderService> logger) : IOrderService
{
    public async Task<Order> CreateAsync(
        CreateOrder command,
        CancellationToken cancellationToken)
    {
        var order = Order.Create(command.CustomerId, clock.UtcNow);

        await repository.AddAsync(order, cancellationToken);
        logger.LogInformation("Order {OrderId} created", order.Id);

        return order;
    }
}

Um endpoint minimal API pode solicitar o serviço como parâmetro. O framework o resolve a partir do contêiner para cada chamada, preservando o controller ou endpoint como uma camada fina de transporte.

app.MapPost("/orders", async (
    CreateOrder command,
    IOrderService orderService,
    CancellationToken cancellationToken) =>
{
    var order = await orderService.CreateAsync(command, cancellationToken);
    return Results.Created($"/orders/{order.Id}", order);
});

Benefícios que aparecem na aplicação

O primeiro benefício é menor acoplamento: trocar EF Core por outro armazenamento ou um provedor de e-mail não obriga a reescrever o caso de uso. O segundo é consistência: logging, opções, clientes HTTP tipados e tratamento de configuração seguem um único ponto de composição. O terceiro é clareza de responsabilidade: um construtor grande é um sinal útil de que a classe pode estar fazendo trabalho demais, não um motivo para usar um service locator.

DI também evita criar HttpClient indiscriminadamente. Registre um cliente tipado para concentrar URL base, headers e resiliência; depois injete-o no adaptador que fala com o serviço externo.

builder.Services.AddHttpClient<IPaymentGateway, PaymentGateway>(client =>
{
    client.BaseAddress = new Uri("https://payments.example");
    client.Timeout = TimeSpan.FromSeconds(10);
});

3. Teste sem infraestrutura real

Como as dependências são contratos, um teste pode fornecer implementações controladas. O exemplo usa um relógio fixo e um repositório em memória, tornando a data e o efeito observado determinísticos. Em projetos reais, mocks, fakes ou bancos de teste devem representar apenas a fronteira necessária ao cenário.

var repository = new InMemoryOrderRepository();
var clock = new FixedClock(new DateTimeOffset(2026, 11, 11, 12, 0, 0, TimeSpan.Zero));
var logger = NullLogger<OrderService>.Instance;
var service = new OrderService(repository, clock, logger);

var order = await service.CreateAsync(
    new CreateOrder(customerId),
    CancellationToken.None);

Assert.Equal(clock.UtcNow, order.CreatedAt);
Assert.Single(repository.Orders);

Cuidados para manter DI útil

Registre serviços no ponto de entrada e injete apenas o que a classe realmente usa. Evite IServiceProvider dentro da lógica de negócio: ele esconde dependências e adia erros de configuração para execução. Valide o grafo na inicialização em desenvolvimento, mantenha ciclos de vida compatíveis e prefira interfaces nas fronteiras que você precisa variar ou testar. Uma interface para cada classe, sem necessidade, não cria flexibilidade automaticamente.

DI não elimina decisões de arquitetura nem substitui testes. Ela cria uma fronteira clara entre a regra e seus detalhes, permitindo que a aplicação evolua com menos alterações em cascata. No .NET 10, o suporte nativo torna essa composição uma parte simples e central do desenho de uma API ou serviço.
