Compressão HTTP em APIs .NET 10: ganhos, riscos e implementação passo a passo

Reduza bytes transferidos sem transformar CPU, observabilidade ou segurança em efeitos colaterais invisíveis.

.NET 10HTTPPerformance

“Request compression” costuma descrever duas direções diferentes. A mais comum é a compressão da resposta: o cliente envia Accept-Encoding e a API devolve JSON, HTML ou texto em Brotli ou Gzip. A outra é uma requisição comprimida: o cliente envia Content-Encoding e o servidor descompacta o corpo antes de processá-lo. Em uma API .NET, as duas podem coexistir, mas têm objetivos, riscos e configuração próprios.

O que a compressão resolve

Compressão troca CPU por menos bytes na rede. JSON repetitivo, CSS, JavaScript, HTML, XML e SVG normalmente comprimem muito bem; imagens JPEG, PNG, WebP, vídeos, arquivos ZIP e dados já codificados em base64 raramente justificam outra passagem. Menos bytes tende a reduzir tempo de transferência, uso de banda e custo de egress, principalmente para clientes móveis, redes distantes ou respostas com muitos registros.

Os ganhos devem ser medidos no tamanho transferido e na latência de ponta a ponta, não apenas no tempo da action. Uma resposta de 500 KB que se torna 80 KB pode chegar mais cedo em uma conexão limitada, embora o servidor e o cliente gastem algum tempo comprimindo e descomprimindo. Em uma LAN rápida e para respostas pequenas, esse custo pode superar o benefício.

Desvantagens, limites e segurança

A compressão adiciona trabalho de CPU, pode aumentar a latência de respostas pequenas e torna métricas de tamanho mais importantes: Content-Length pode desaparecer porque o corpo é produzido em streaming. Níveis mais altos reduzem mais bytes, mas custam mais CPU; por isso, o melhor nível é uma decisão medida sob carga representativa, não uma regra universal.

Há também um limite de segurança. Em respostas HTTPS que misturam um segredo com conteúdo controlável pelo atacante, a variação do tamanho comprimido pode revelar informações por ataques como BREACH. ASP.NET Core mantém a compressão de respostas HTTPS desabilitada por padrão. Só habilite EnableForHttps quando tiver analisado as respostas: não comprima páginas que reflitam entrada controlada junto de tokens, cookies ou segredos e mantenha proteção CSRF, autorização e cache adequados.

Para corpos recebidos, aceite apenas codificações que você suporta e imponha limites depois da descompressão. Um corpo comprimido pequeno pode expandir muito: sem limite de tamanho, tempo limite e rate limiting, ele vira uma forma de exaurir memória, CPU ou disco. A descompressão não substitui validação de payload nem limites do proxy e do Kestrel.

Passo a passo: comprimir respostas

1. Crie ou atualize uma Web API que use o SDK Microsoft.NET.Sdk.Web e tenha como alvo net10.0. Response compression faz parte do framework compartilhado do ASP.NET Core; não é necessário instalar um pacote NuGet para a configuração abaixo.

dotnet new webapi --framework net10.0 --name CompressionApi
cd CompressionApi

2. Registre os provedores e os tipos de conteúdo que fazem sentido para a API. Brotli costuma produzir corpos menores, enquanto Gzip é amplamente compatível. O middleware negocia o algoritmo com o cabeçalho Accept-Encoding do cliente; não é preciso escolher um algoritmo em cada endpoint.

using Microsoft.AspNetCore.ResponseCompression;
using System.IO.Compression;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddResponseCompression(options =>
{
    options.EnableForHttps = true; // Habilite somente após avaliar o risco de BREACH.
    options.Providers.Add<BrotliCompressionProvider>();
    options.Providers.Add<GzipCompressionProvider>();
    options.MimeTypes = ResponseCompressionDefaults.MimeTypes.Concat([
        "application/json",
        "application/problem+json",
        "application/xml",
        "image/svg+xml"
    ]);
});

builder.Services.Configure<BrotliCompressionProviderOptions>(options =>
    options.Level = CompressionLevel.Fastest);
builder.Services.Configure<GzipCompressionProviderOptions>(options =>
    options.Level = CompressionLevel.Fastest);

3. Adicione o middleware cedo no pipeline. Se a aplicação serve arquivos estáticos e você quer que eles também possam ser comprimidos, UseResponseCompression deve aparecer antes de UseStaticFiles. Para uma API pura, coloque-o antes dos endpoints que escrevem a resposta.

var app = builder.Build();

app.UseResponseCompression();
app.UseHttpsRedirection();

app.MapGet("/products", () =>
{
    var products = Enumerable.Range(1, 1_000).Select(id => new
    {
        id,
        Name = $"Product {id}",
        Description = "A description with repeated text that compresses well."
    });

    return Results.Ok(products);
});

app.Run();

O middleware só comprime uma resposta elegível quando o cliente aceita uma codificação e o Content-Type é permitido. Ele acrescenta Content-Encoding e Vary: Accept-Encoding, para que caches não devolvam por engano uma variante Brotli a um cliente que só aceita Gzip. Não force Content-Encoding manualmente e não comprima novamente dados já comprimidos.

Passo a passo: aceitar requisições comprimidas

O middleware de descompressão de requisições lê Content-Encoding e expõe o corpo descompactado aos model binders e endpoints seguintes. Registre-o nos serviços e adicione-o antes dos endpoints que leem Request.Body. O suporte padrão cobre Gzip e Brotli; um Content-Encoding ausente preserva o comportamento normal.

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddRequestDecompression();

var app = builder.Build();

app.UseRequestDecompression();

app.MapPost("/imports", async (HttpRequest request, CancellationToken cancellationToken) =>
{
    using var reader = new StreamReader(request.Body);
    var json = await reader.ReadToEndAsync(cancellationToken);

    // Desserialize, valide o contrato e aplique limites de domínio aqui.
    return Results.Accepted("/imports/123", new { receivedBytes = json.Length });
});

app.Run();

O cliente deve informar exatamente a codificação aplicada. Este exemplo comprime um JSON com Gzip e o envia para a rota. Em aplicações reais, prefira streaming e limites no servidor a carregar corpos grandes inteiros na memória como o exemplo didático faz.

gzip -c import.json > import.json.gz
curl -i -X POST http://localhost:5000/imports \
  -H "Content-Type: application/json" \
  -H "Content-Encoding: gzip" \
  --data-binary @import.json.gz

Como verificar e operar

Teste a negociação da resposta com curl. A opção --compressed envia um Accept-Encoding suportado e descompacta a resposta para exibição. Para inspecionar cabeçalhos, observe Content-Encoding e Vary; compare o tamanho no proxy, nas métricas de egress ou em uma captura HTTP, não apenas o texto já descompactado que curl imprime.

curl --compressed -i http://localhost:5000/products
curl -s -D - -o /dev/null \
  -H "Accept-Encoding: br, gzip" \
  http://localhost:5000/products

Antes de publicar, descubra onde a compressão realmente acontece. Um CDN, ingress, Nginx, IIS ou balanceador pode comprimir respostas antes de elas chegarem ao cliente. Escolha uma camada responsável, evite dupla compressão e preserve Vary: Accept-Encoding. Meça CPU da aplicação, latência p50/p95/p99, tamanho original e transferido, taxa de respostas por Content-Encoding e erros de descompressão.

Uma decisão prática

Comece com respostas textuais suficientemente grandes, Brotli e Gzip, nível Fastest e métricas. Exclua mídia e arquivos já compactados. Habilite HTTPS apenas após revisar os fluxos que expõem segredos. Para requisições comprimidas, adote o middleware apenas quando clientes enviam corpos grandes com benefício mensurável e combine-o com limites de tamanho descompactado, timeouts e rate limiting. Assim, compressão vira uma otimização explícita e observável, não uma aposta global.
