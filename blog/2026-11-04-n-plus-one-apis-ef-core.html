O problema N+1 em APIs: como identificá-lo e evitá-lo com EF Core

Uma lista aparentemente simples pode disparar uma consulta inicial e mais uma para cada item retornado.

.NET 10EF CorePerformance

N+1 é um problema de acesso a dados muito comum em APIs. A aplicação faz uma consulta para buscar uma lista de entidades e, ao percorrê-la, executa outra consulta para cada entidade a fim de carregar uma relação. Com 50 pedidos, por exemplo, a requisição pode produzir 51 comandos SQL: um para os pedidos e 50 para seus itens.

O efeito vai além do número exibido no log. Cada ida ao banco acrescenta latência, ocupa conexões e amplia o trabalho do servidor. Em desenvolvimento, uma base pequena e local pode esconder o custo; em produção, uma página maior, uma rede mais lenta ou concorrência suficiente transforma a rota em um gargalo.

Um modelo de pedidos

Considere uma API que lista pedidos e precisa retornar a quantidade de itens de cada um. Para demonstrar o problema com clareza, o exemplo habilita lazy loading proxies. Essa configuração é opcional no EF Core, mas quando está habilitada, acessar uma navegação ainda não carregada pode executar SQL de forma implícita.

public sealed class Order
{
    public int Id { get; set; }
    public DateTimeOffset CreatedAt { get; set; }
    public virtual ICollection<OrderItem> Items { get; set; } = [];
}

public sealed class OrderItem
{
    public int Id { get; set; }
    public int OrderId { get; set; }
    public decimal UnitPrice { get; set; }
    public int Quantity { get; set; }
}

builder.Services.AddDbContext<StoreDbContext>(options =>
    options.UseSqlServer(connectionString)
        .UseLazyLoadingProxies()
        .EnableSensitiveDataLogging()); // Use somente no desenvolvimento.

Como o N+1 acontece

A rota abaixo parece inofensiva. O primeiro ToListAsync busca os pedidos. Depois, cada acesso a order.Items.Count pode acionar o carregamento lento para aquele pedido. Se a página contém 20 pedidos, são 21 consultas; se contém 100, são 101.

app.MapGet("/orders", async (StoreDbContext db, CancellationToken cancellationToken) =>
{
    var orders = await db.Orders
        .OrderByDescending(order => order.CreatedAt)
        .Take(20)
        .ToListAsync(cancellationToken);

    return orders.Select(order => new
    {
        order.Id,
        order.CreatedAt,
        ItemCount = order.Items.Count
    });
});

Com o log de comandos do EF Core habilitado, o padrão é fácil de reconhecer: um SELECT para Orders, seguido de vários SELECTs filtrados por OrderId. Conte os comandos de uma única requisição e teste com uma quantidade realista de registros; medir apenas o tempo local pode não revelar o problema.

A opção preferida: projete a resposta

Em uma API, normalmente não é necessário materializar toda a entidade nem todos os itens para devolver um resumo. Projete exatamente o contrato da resposta dentro da consulta. EF Core traduz a agregação sobre a navegação para SQL, e o banco calcula a contagem sem uma viagem adicional por pedido.

public sealed record OrderListItem(
    int Id,
    DateTimeOffset CreatedAt,
    int ItemCount,
    decimal Total);

app.MapGet("/orders", async (StoreDbContext db, CancellationToken cancellationToken) =>
{
    var orders = await db.Orders
        .AsNoTracking()
        .OrderByDescending(order => order.CreatedAt)
        .Take(20)
        .Select(order => new OrderListItem(
            order.Id,
            order.CreatedAt,
            order.Items.Count,
            order.Items.Sum(item => item.UnitPrice * item.Quantity)))
        .ToListAsync(cancellationToken);

    return Results.Ok(orders);
});

Além de evitar o N+1, a projeção reduz colunas e objetos materializados. AsNoTracking é adequado para leitura quando as entidades não serão alteradas naquele contexto. Confira o SQL gerado e o plano de execução no provedor usado pela aplicação, especialmente quando as agregações ou filtros ficarem mais complexos.

Quando a resposta precisa da coleção

Se o contrato realmente precisa dos itens, carregue a relação de forma explícita. Include evita uma consulta por pedido, mas uma coleção grande combinada com outras coleções pode gerar muitas linhas repetidas em um único JOIN. AsSplitQuery pode dividir Includes de coleções em poucas consultas planejadas — não uma por entidade — e pode ser uma escolha melhor quando a explosão cartesiana for o risco principal.

var orders = await db.Orders
    .AsNoTracking()
    .OrderByDescending(order => order.CreatedAt)
    .Take(20)
    .Include(order => order.Items)
    .AsSplitQuery()
    .ToListAsync(cancellationToken);

Como prevenir o problema

Escolha a estratégia a partir do formato da resposta: projeção para DTOs de leitura; Include para um grafo que será realmente usado; carregamento explícito quando a relação é condicional e controlada. Evite serializar entidades rastreadas diretamente, pois o serializador ou código de mapeamento pode tocar em navegações inesperadas. Em rotas críticas, considere não habilitar lazy loading e trate cada carregamento de relação como uma decisão visível no código.

N+1 não é uma peculiaridade do EF Core: é a consequência de consultar dados relacionados sem planejar o acesso. O remédio não é adicionar Include em toda consulta, mas definir o que a API precisa devolver, carregar isso de forma explícita e verificar os comandos SQL. Assim, o custo da rota continua previsível quando a lista cresce.
