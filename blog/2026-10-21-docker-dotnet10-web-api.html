Docker no desenvolvimento de software: dos contêineres a uma Web API .NET 10

Entenda o que é Docker e sua importância no desenvolvimento; depois, crie, containerize e execute uma Web API .NET 10 com uma imagem multi-stage preparada para deploy.

Contêineres Fluxo de desenvolvimento .NET 10

“Funciona na minha máquina” é um problema conhecido em equipes de software. Um serviço pode depender de uma versão específica do runtime, biblioteca nativa, banco de dados ou variável de ambiente; outra pessoa da equipe ou o ambiente de deploy talvez não tenha a mesma configuração. O Docker ajuda a tornar essas dependências explícitas e a empacotar a aplicação para que ela rode de forma consistente nos ambientes compatíveis.

O que é Docker?

Docker é uma plataforma e um conjunto de ferramentas para criar, distribuir e executar aplicações em contêineres. Um contêiner é um processo isolado que usa o kernel do sistema operacional hospedeiro e inclui a aplicação e as dependências de espaço de usuário necessárias. Ele é mais leve que uma máquina virtual, que normalmente inclui um sistema operacional completo próprio, mas não é uma fronteira de segurança que dispense isolamento, atualizações ou configuração adequada.

Uma imagem é o pacote versionado, em grande parte somente leitura, usado para iniciar contêineres; um contêiner é uma instância em execução de uma imagem. Um Dockerfile descreve as etapas para criar uma imagem. Essas etapas geram camadas que podem ser armazenadas em cache e reutilizadas, tornando builds repetidos mais rápidos quando as entradas não mudam. Um registry armazena e distribui imagens, enquanto o Docker Engine as executa em uma máquina.

Por que Docker é importante no desenvolvimento?

Um contêiner oferece aos desenvolvedores, pipelines de CI e plataformas de deploy uma base de runtime mais consistente. Ele ajuda a documentar pacotes do sistema operacional, versões de runtime, portas e comandos de inicialização como código; facilita testar uma dependência sem instalá-la globalmente; e reduz diferenças de configuração que causam falhas do tipo “funciona na minha máquina”. Isso não garante que todos os ambientes se comportem de forma idêntica: configuração, serviços externos, arquitetura de CPU e dados de produção continuam importantes.

Por exemplo, uma equipe pode usar localmente a mesma versão do banco de dados usada pela CI, iniciar um cache para um teste de integração sem instalá-lo em cada computador ou criar uma imagem uma única vez e promover esse artefato pelos ambientes de teste e produção. Contêineres também ajudam a separar uma aplicação em serviços construídos de forma independente. Eles não são automaticamente mais rápidos nem mais simples: projetos pequenos talvez não precisem deles, e dados persistentes, rede, segredos e monitoramento ainda exigem decisões cuidadosas.

Um fluxo prático de desenvolvimento

Uma pessoa desenvolvedora pode iniciar um contêiner Redis descartável para trabalhar em uma integração local, mapeando apenas a porta necessária para a aplicação. A tag da imagem deixa visível a versão escolhida; `--rm` remove o contêiner quando ele é encerrado. Para uma equipe que precisa executar vários serviços juntos, Docker Compose pode descrever a aplicação, o banco de dados, as redes e os volumes em um único arquivo.

Inicie um serviço Redis temporário para desenvolvimento local

docker run --rm --name local-cache -d -p 6379:6379 redis:7
docker stop local-cache

Exemplo: crie uma Web API .NET 10

O exemplo usa o SDK do .NET 10 e uma pequena API ASP.NET Core. Crie o projeto e substitua o `Program.cs` por esta Minimal API. A rota `/api/products` retorna um JSON de exemplo, enquanto `/health` oferece um endpoint simples para verificar se o processo está respondendo. Em um serviço real, health checks devem refletir as dependências e os critérios de prontidão importantes para aquela aplicação.

Crie um projeto Web API .NET 10

dotnet new webapi --name Catalog.Api --framework net10.0 --no-https
cd Catalog.Api

Catalog.Api/Program.cs

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/health", () => Results.Ok(new { status = "healthy" }));

app.MapGet("/api/products", () => Results.Ok(new[]
{
    new { id = 1, name = "Keyboard", price = 79.99 },
    new { id = 2, name = "Mouse", price = 39.99 }
}));

app.Run();

Crie uma imagem pequena e pronta para deploy

Use um Dockerfile multi-stage: a imagem do SDK restaura e publica a aplicação; a imagem final contém apenas o runtime ASP.NET Core e os arquivos publicados. Copiar o arquivo do projeto antes do restante do código permite reutilizar a camada de restore quando somente o código da aplicação muda. O contêiner escuta na porta HTTP 8080, porta não privilegiada padrão nas imagens atuais de contêiner .NET. `USER $APP_UID` executa o processo como o usuário não root fornecido pela imagem oficial.

Catalog.Api/Dockerfile

FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

COPY ["Catalog.Api.csproj", "./"]
RUN dotnet restore "./Catalog.Api.csproj"
COPY . .
RUN dotnet publish "./Catalog.Api.csproj" -c Release -o /app/publish --no-restore /p:UseAppHost=false

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app
ENV ASPNETCORE_HTTP_PORTS=8080
EXPOSE 8080
USER $APP_UID
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "Catalog.Api.dll"]

O Dockerfile configura a porta HTTP do contêiner, mas não a publica no host por conta própria. `EXPOSE` documenta a porta; `-p` no momento da execução cria o mapeamento entre host e contêiner. A aplicação deve ler configurações específicas do ambiente por meio da configuração padrão, e os segredos devem ser fornecidos pela plataforma de deploy, não copiados para a imagem nem commitados no repositório.

Mantenha o contexto de build limpo

O arquivo `.dockerignore` impede que artefatos locais de build, arquivos do editor, histórico do Git e configurações locais sejam enviados ao build do Docker. Isso reduz o tamanho do contexto e a chance de empacotar acidentalmente arquivos que não pertencem à imagem.

Catalog.Api/.dockerignore

**/bin/
**/obj/
.git/
.vs/
*.user
*.suo

Faça build, execute e verifique localmente

Execute estes comandos no diretório `Catalog.Api`, onde está o Dockerfile. O primeiro cria uma imagem com tag; o segundo inicia um contêiner descartável e mapeia a porta 8080 do host para a porta 8080 do contêiner. Acesse o endpoint pelo navegador ou use curl para conferir a resposta.

Crie a imagem e inicie o contêiner

docker build -t catalog-api:1.0 .
docker run --rm --name catalog-api -p 8080:8080 catalog-api:1.0

Verifique a resposta da API

curl http://localhost:8080/health
curl http://localhost:8080/api/products

Ao terminar, pare o processo em primeiro plano com Ctrl+C; como foi usado `--rm`, o contêiner encerrado será removido automaticamente. A imagem continua disponível até ser removida. Em uma stack real de desenvolvimento, Compose pode gerenciar serviços e volumes nomeados, enquanto o código da aplicação ainda deve seguir o fluxo de desenvolvimento adequado quando for importante editar e recarregar rapidamente.

O que muda antes do deploy?

Uma imagem de contêiner é um artefato implantável, não uma estratégia completa de deploy. Crie e teste a imagem na CI, use uma tag baseada no commit ou release, publique-a em um registry confiável e implante exatamente essa imagem no ambiente de destino. Forneça configurações e segredos em runtime, exponha somente as portas necessárias, defina limites de recursos e verificações de saúde, e mantenha os dados persistentes fora da camada gravável do contêiner. Termine HTTPS na plataforma ou em um proxy reverso configurado corretamente e mantenha imagens-base e dependências atualizadas.

Conclusão

Docker torna o runtime e o empacotamento de uma aplicação mais reproduzíveis, o que melhora o desenvolvimento local, os testes automatizados e a entrega. O valor vem de um build claro da imagem, configuração explícita e um processo de deploy que trata a imagem como artefato imutável — não de colocar toda aplicação em um contêiner por padrão. O exemplo com .NET 10 reúne essas ideias: build multi-stage, runtime não root, porta HTTP definida e uma API pequena que pode ser construída e executada com poucos comandos.
