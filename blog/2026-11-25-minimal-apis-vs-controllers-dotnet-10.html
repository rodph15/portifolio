Minimal APIs ou Controllers no .NET 10: diferenças, vantagens e desvantagens

Minimal APIs e Controllers resolvem o mesmo problema — expor endpoints HTTP — mas organizam o código de maneiras diferentes. Entenda as features, os trade-offs e como escolher uma abordagem sem transformar preferência em regra.

Minimal APIsControllers.NET 10

No ASP.NET Core, uma API HTTP pode ser construída com endpoints definidos diretamente no pipeline ou com classes que representam controllers. No .NET 10, as duas opções continuam sendo suportadas, recebem integração com DI, OpenAPI, autenticação, autorização, validação e observabilidade. A diferença principal está na forma de expressar o transporte HTTP e separar responsabilidades — não em uma suposta diferença de capacidade fundamental.

A diferença fundamental

Uma Minimal API mapeia uma rota para um delegate ou método de handler. O endpoint fica próximo do registro da aplicação e suas dependências podem ser parâmetros do método. Um Controller organiza ações dentro de uma classe derivada de ControllerBase; atributos como [HttpGet], [Route] e [ApiController] descrevem o contrato. Em ambos os casos, o runtime executa routing, model binding, filtros ou middleware, autorização e serialização.

Exemplo de Minimal API

Para um catálogo pequeno, o ponto de entrada pode registrar os serviços e mapear os endpoints de forma direta. O resultado é curto, explícito e fácil de acompanhar de cima para baixo.

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddSingleton<ProductService>();
builder.Services.AddOpenApi();

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
}

app.MapGet("/api/products/{id:int}", async (int id, ProductService service, CancellationToken ct) =>
{
    var product = await service.FindAsync(id, ct);
    return product is null ? Results.NotFound() : Results.Ok(product);
})
.WithName("GetProduct")
.WithTags("Products")
.RequireAuthorization();

app.MapPost("/api/products", async (CreateProductRequest request, ProductService service, CancellationToken ct) =>
{
    var product = await service.CreateAsync(request, ct);
    return Results.Created($"/api/products/{product.Id}", product);
})
.WithName("CreateProduct")
.WithTags("Products");

app.Run();

Nesse exemplo, o binding converte o segmento {id} para int, injeta ProductService pelo container e fornece o CancellationToken da requisição. Métodos como WithName, WithTags, RequireAuthorization e metadados de OpenAPI tornam o contrato mais descritivo sem exigir uma classe de controller.

Exemplo com Controller

A mesma API pode usar uma classe dedicada. O atributo [ApiController] habilita convenções úteis, como inferência de origem dos parâmetros, respostas de validação e erros HTTP padronizados. O método pode retornar ActionResult<T> para combinar dados e resultados HTTP.

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();
builder.Services.AddOpenApi();
builder.Services.AddSingleton<ProductService>();

var app = builder.Build();

if (app.Environment.IsDevelopment())
{
    app.MapOpenApi();
}

app.MapControllers();
app.Run();

[ApiController]
[Route("api/[controller]")]
public sealed class ProductsController(ProductService service) : ControllerBase
{
    [HttpGet("{id:int}")]
    [Authorize]
    public async Task<ActionResult<Product>> Get(int id, CancellationToken ct)
    {
        var product = await service.FindAsync(id, ct);
        return product is null ? NotFound() : Ok(product);
    }

    [HttpPost]
    public async Task<ActionResult<Product>> Create(
        [FromBody] CreateProductRequest request,
        CancellationToken ct)
    {
        var product = await service.CreateAsync(request, ct);
        return CreatedAtAction(nameof(Get), new { id = product.Id }, product);
    }
}

O controller oferece uma fronteira explícita para um conjunto de ações relacionadas. Atributos documentam o contrato perto da ação, filtros podem atuar antes ou depois dela e convenções de API ajudam a manter respostas previsíveis. Em projetos maiores, isso pode facilitar a navegação e a divisão do trabalho entre equipes.

Features comuns e diferenças práticas

A escolha não elimina os recursos do ASP.NET Core. Middleware, DI, configuração, logging, autenticação, autorização, health checks, rate limiting, output caching e OpenAPI podem ser usados nas duas abordagens. O que muda é a superfície de composição.

  • Routing: Minimal APIs usam MapGet, MapPost e route groups; Controllers usam atributos ou convenções de rota.
  • Binding: Minimal APIs inferem parâmetros do delegate e aceitam atributos como [FromBody]; Controllers combinam inferência com o comportamento de [ApiController].
  • Cross-cutting: Minimal APIs têm endpoint filters e grupos; Controllers têm action filters, authorization filters e filtros globais.
  • OpenAPI: ambas podem publicar metadados, nomes, tags, summaries e respostas para gerar documentação.
  • Testes: ambas podem ser testadas com WebApplicationFactory; handlers pequenos também podem ser isolados como funções ou serviços.

Vantagens e desvantagens em comparação

Onde Minimal APIs brilham

Elas reduzem cerimônia, deixam o fluxo de uma API pequena visível em poucos arquivos e funcionam muito bem para microserviços, endpoints internos, health checks, protótipos e APIs orientadas a poucos casos de uso. Route groups permitem aplicar prefixos e metadados comuns sem duplicação. Também é natural manter cada endpoint próximo do seu contrato e da composição necessária.

Limites das Minimal APIs

Quando muitos endpoints, regras e filtros crescem no mesmo arquivo, a concisão pode virar concentração de responsabilidades. A expressão com delegates também pode ficar menos familiar para equipes acostumadas a APIs ASP.NET Core baseadas em atributos. É preciso criar módulos, grupos, handlers e serviços deliberadamente; caso contrário, o Program.cs vira um novo controller gigante.

Onde Controllers brilham

Controllers oferecem uma organização convencional, fácil de reconhecer em equipes que usam APIs baseadas em atributos e convenções do ASP.NET Core, além de uma rica infraestrutura de filtros. A separação por recurso, políticas de convenção, action results e filtros globais ajuda quando a API tem muitos endpoints ou precisa seguir padrões consistentes. Também é uma boa escolha quando a equipe já possui bibliotecas, testes e práticas construídos em torno de controllers.

Limites dos Controllers

A estrutura pode adicionar cerimônia para uma API simples: classes, atributos e métodos pequenos podem esconder o fluxo real. Controllers também podem acumular lógica de negócio ou depender demais de filtros implícitos. A solução não é abandonar controllers, mas manter as ações finas e mover regras para serviços e casos de uso testáveis.

Performance: o que as evidências mostram

Em benchmarks focados no pipeline HTTP, Minimal APIs tendem a apresentar menor overhead e maior throughput do que Controllers, porque percorrem menos infraestrutura de ativação, convenções e filtros. A própria documentação do ASP.NET Core classifica Minimal APIs como uma abordagem de alta performance e aponta overhead reduzido em comparação com Controllers. Isso é uma diferença real, mas não significa que uma aplicação completa será automaticamente mais rápida: consultas ao banco, chamadas externas, serialização, autenticação, logging e regras de negócio normalmente dominam o tempo total.

A evidência precisa ser interpretada pelo tipo de teste. O repositório oficial de benchmarks do ASP.NET Core mede cenários controlados, úteis para acompanhar o custo do framework. Ele não representa o comportamento de todo domínio, banco ou infraestrutura. Para decidir, compare endpoints equivalentes, mesmo payload, mesma autenticação, mesmos middlewares, mesma versão do .NET e carga realista. Meça throughput, latência p95/p99, alocações e consumo de CPU; depois confirme com profiling em produção ou staging.

Na prática, não escolha Minimal APIs apenas por uma diferença de benchmark sintético, nem descarte Controllers por alguns microssegundos de overhead. Se o endpoint é um proxy simples ou uma rota de alta frequência, a diferença pode importar. Se ele espera 80 ms no banco, economizar uma fração desse tempo no transporte provavelmente não será o gargalo. Performance deve ser uma decisão baseada em medição, não em slogan.

Como escolher

Escolha Minimal APIs quando a prioridade for baixo overhead estrutural, poucos endpoints, composição explícita ou uma aplicação organizada por features. Escolha Controllers quando convenções de equipe, filtros baseados em atributos, muitos endpoints e uma separação familiar por recursos trouxerem mais clareza. Em um sistema real, é possível usar as duas abordagens: por exemplo, controllers para uma área pública tradicional e Minimal APIs para endpoints internos ou módulos novos. O importante é não misturar estilos sem uma regra de organização.

A melhor abstração é a que mantém o contrato claro

Minimal APIs não são automaticamente mais performáticas, assim como Controllers não são automaticamente mais enterprise. O custo decisivo costuma estar em banco, rede, serialização e regras de negócio, não na quantidade de classes do transporte. Compare legibilidade, testabilidade, observabilidade, experiência da equipe e evolução esperada. Uma API bem desenhada mantém endpoints finos, contratos explícitos e responsabilidades fora da camada HTTP — independentemente da sintaxe escolhida.
