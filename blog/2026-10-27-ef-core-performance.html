Melhorando a performance com EF Core: consultas práticas sem excessos

Veja como evitar explosão cartesiana, projetar apenas os dados necessários, paginar com consistência e escolher views quando uma consulta complexa merece uma fronteira no banco.

PerformanceEF CoreSQL

Performance com EF Core começa com uma pergunta: qual SQL esta expressão LINQ vai gerar e quantos dados ela vai transferir? O ORM não é inerentemente lento, mas uma consulta conveniente pode buscar linhas repetidas, todas as colunas de uma tabela larga ou um resultado inteiro quando a tela precisa apenas de uma página.

SelectMany e a explosão cartesiana

A explosão cartesiana acontece quando uma consulta combina múltiplos relacionamentos de coleção em um resultado. Um pedido com 10 itens e 5 envios pode retornar 50 linhas ao achatar as duas coleções. SelectMany é útil quando esse resultado é realmente necessário, mas deve ser uma decisão consciente: cada coleção adicional multiplica as linhas retornadas.

// Achate apenas quando uma linha por item for o resultado desejado.
var items = await db.Orders.Where(o => o.Id == orderId)
    .SelectMany(o => o.Items, (o, item) => new { o.Id, item.ProductName })
    .ToListAsync(cancellationToken);

var order = await db.Orders.AsNoTracking().AsSplitQuery()
    .Include(o => o.Items).Include(o => o.Shipments)
    .SingleAsync(o => o.Id == orderId, cancellationToken);

Para um modelo que precisa do pedido e resumos separados dos filhos, projete o formato necessário. Se precisar de Include para múltiplas coleções, AsSplitQuery() pode evitar um join grande ao emitir consultas separadas para as coleções incluídas. É uma troca entre menos linhas duplicadas e mais viagens ao banco; meça com dados reais.

Leia somente o que o endpoint precisa

AsNoTracking() é um bom padrão para endpoints somente de leitura: ele evita o custo de manter change tracking para entidades que não serão alteradas. Combine-o com uma projeção para DTO; selecionar poucos campos evita carregar uma descrição grande, colunas de auditoria ou coleções inteiras sem necessidade.

var products = await db.Products.AsNoTracking()
    .Where(p => p.IsActive).OrderBy(p => p.Name)
    .Select(p => new { p.Id, p.Name, p.Price, ReviewCount = p.Reviews.Count })
    .ToListAsync(cancellationToken);

Mantenha a consulta como IQueryable até executá-la

IQueryable representa uma consulta que o EF Core ainda pode traduzir para SQL. Componha filtros, ordenação, projeção e paginação antes de chamar ToListAsync ou outra operação terminal. Materializar cedo transforma filtros posteriores em trabalho em memória e pode fazer o banco retornar muito mais linhas que o necessário.

IQueryable<Product> query = db.Products.AsNoTracking();
if (!string.IsNullOrWhiteSpace(search)) query = query.Where(p => p.Name.Contains(search));
var pageItems = await query.OrderBy(p => p.Name).ThenBy(p => p.Id)
    .Select(p => new { p.Id, p.Name, p.Price })
    .Skip((page - 1) * pageSize).Take(pageSize).ToListAsync(cancellationToken);

Paginação com ordenação estável

Use OrderBy antes de Skip e Take; sem uma ordem determinística, páginas podem repetir ou omitir linhas. Valide e limite o tamanho da página, e projete antes de materializar. Para listas muito profundas e que mudam com frequência, paginação por chave, baseada na última chave indexada vista, pode ser mais adequada que offset.

Quando uma consulta complexa merece uma view

Um relatório complexo pode ser mais fácil de revisar, otimizar e reutilizar como uma view do banco. A view centraliza joins e agregações, enquanto o EF Core mapeia o resultado para um tipo sem chave. Ela não torna a consulta rápida automaticamente: os índices das tabelas de origem e o plano de execução continuam importantes.

CREATE VIEW reporting.CustomerOrderSummary AS
SELECT c.Id AS CustomerId, c.Name, COUNT(o.Id) AS OrderCount,
       COALESCE(SUM(o.Total), 0) AS TotalSpent
FROM Customers c LEFT JOIN Orders o ON o.CustomerId = c.Id AND o.Status = 'Paid'
GROUP BY c.Id, c.Name;
public sealed class CustomerOrderSummary { public int CustomerId { get; init; } public string Name { get; init; } = ""; public decimal TotalSpent { get; init; } }
modelBuilder.Entity<CustomerOrderSummary>().HasNoKey().ToView("CustomerOrderSummary", "reporting");
var topCustomers = await db.Set<CustomerOrderSummary>().AsNoTracking()
    .Where(c => c.TotalSpent >= minimumSpent).OrderByDescending(c => c.TotalSpent)
    .Take(20).ToListAsync(cancellationToken);

Meça antes de otimizar

A regra prática não é “nunca use Include” ou “sempre use uma view”. Comece com o menor formato de dados que atende ao caso de uso, mantenha a composição do lado do banco, inspecione o SQL gerado e meça antes e depois de uma mudança pontual.
