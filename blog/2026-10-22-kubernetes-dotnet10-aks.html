Kubernetes do zero: conceitos, cloud e uma Web API .NET 10 no AKS

Entenda para que serve o Kubernetes, como escolher um serviço gerenciado na cloud e como criar, publicar e testar uma Web API .NET 10 em um cluster Azure Kubernetes Service.

Kubernetes Cloud .NET 10

Contêineres empacotam aplicações, mas operar dezenas ou centenas deles traz outras perguntas: em qual máquina cada um deve rodar? O que acontece se um processo falhar? Como distribuir tráfego, atualizar versões sem interromper usuários e aumentar ou reduzir a capacidade? Kubernetes — frequentemente abreviado como K8s — automatiza parte dessa operação por meio de um estado desejado que o cluster tenta manter.

O que é Kubernetes e para que serve?

Kubernetes é uma plataforma open source para orquestrar aplicações em contêineres. Você declara recursos como réplicas, imagens, portas e verificações de saúde; os controladores do cluster observam a diferença entre o estado atual e o desejado e trabalham continuamente para reconciliá-la. Se um Pod deixa de responder, por exemplo, o controlador pode criar outro. Kubernetes não cria automaticamente uma arquitetura correta nem substitui Docker para construir imagens: ele agenda e gerencia workloads em um cluster.

Como um cluster funciona?

O control plane coordena o cluster. O API server recebe as operações e expõe a API; o etcd armazena o estado do cluster; o scheduler escolhe em qual nó um Pod pode ser executado; e o controller manager executa controladores que reconciliam o estado desejado. Em um serviço gerenciado, o provedor opera boa parte dessa camada para você.

Os worker nodes executam as aplicações. O kubelet, agente de cada nó, conversa com o control plane e mantém os Pods solicitados; um runtime compatível com Kubernetes executa os contêineres. Um Pod é a menor unidade implantável e pode conter um ou mais contêineres que compartilham rede e volumes. Na prática, Deployments gerenciam réplicas e atualizações; Services dão um endereço estável a um conjunto de Pods; e Ingress ou Gateway API ajudam a expor tráfego HTTP(S), normalmente com um controlador ou gateway instalado.

ConfigMaps guardam configuração não confidencial, enquanto Secrets representam dados sensíveis — mas seus valores não devem ser tratados como protegidos só por estarem em um Secret: configure controles de acesso e criptografia em repouso. Volumes persistentes permitem solicitar armazenamento que sobrevive à recriação de Pods. Namespaces organizam recursos; labels e selectors conectam objetos. A configuração declarativa costuma ser mantida em YAML e aplicada pela API do cluster.

Vantagens e limites

Kubernetes padroniza a implantação de contêineres em diferentes ambientes, mantém réplicas, oferece descoberta de serviços e permite atualizações graduais e reversões. Também integra verificações de saúde, limites de recursos, armazenamento, configuração e políticas de escala. Isso facilita automatizar operações repetitivas e dá às equipes uma plataforma comum para várias aplicações.

Essa flexibilidade tem custo: há conceitos, configuração, rede, permissões, observabilidade e atualizações do cluster para aprender e operar. Kubernetes não torna um sistema automaticamente mais barato, seguro ou altamente disponível; réplicas precisam de capacidade, dados precisam de estratégia de backup e uma aplicação distribuída exige monitoramento e testes. Para uma aplicação simples, uma plataforma de aplicação gerenciada ou um único contêiner pode ser mais econômico e fácil de manter. Adote Kubernetes quando os requisitos justificarem a complexidade operacional.

Quais serviços de Kubernetes existem na cloud?

Os serviços gerenciados reduzem o trabalho com o control plane e, conforme o produto e a configuração, ajudam a operar nós, rede, atualizações e integração com identidade e registry. Entre as opções mais conhecidas estão Azure Kubernetes Service (AKS), Amazon Elastic Kubernetes Service (EKS) e Google Kubernetes Engine (GKE). Todos executam Kubernetes, mas diferem em identidade, rede, observabilidade, integração com serviços do provedor, preço e detalhes de operação.

No Azure, AKS é a opção gerenciada; AKS Automatic oferece uma experiência mais opinativa e automatizada para clusters compatíveis. Na AWS, EKS inclui EKS Auto Mode para automatizar mais partes da infraestrutura de compute e rede. No Google Cloud, GKE Autopilot gerencia a infraestrutura de nós, enquanto o modo Standard dá mais controle. Também há serviços como DigitalOcean Kubernetes, Oracle Kubernetes Engine e ofertas gerenciadas de outros provedores. Compare regiões disponíveis, suporte, custos do plano de controle e dos nós, balanceadores, armazenamento, tráfego de saída e limites de cada serviço. “Gerenciado” não significa que o provedor administra sua aplicação, seus manifests ou todas as atualizações por você.

Instale Kubernetes para aprender localmente

Para um laboratório, use um cluster local descartável em vez de começar por uma assinatura cloud. Instale Docker e kubectl, além de uma ferramenta de cluster como kind (Kubernetes in Docker) ou Minikube. No macOS, com Docker Desktop e Homebrew instalados, o comando abaixo instala kubectl e kind; em Windows ou Linux, siga os passos oficiais correspondentes ao seu sistema. Docker Desktop também pode oferecer Kubernetes integrado. O kind cria um cluster de nó único no computador; ele é útil para aprender comandos e testar manifests, mas não representa uma arquitetura de produção nem fornece um endpoint público.

No macOS com Homebrew, instale as ferramentas e crie um cluster

brew install kubectl kind
kubectl version --client
kind create cluster --name dotnet-lab
kubectl cluster-info
kubectl get nodes

O kubectl é o cliente de linha de comando para a API Kubernetes. Em um computador local, configure o contexto correto antes de aplicar recursos; comandos de instalação e requisitos mudam conforme o sistema operacional, portanto use a documentação oficial de kubectl e kind. Ao terminar o laboratório, remova somente o cluster local nomeado com `kind delete cluster --name dotnet-lab`.

Crie uma Web API em C# com .NET 10

O exemplo usa uma Minimal API ASP.NET Core sem banco de dados para manter o tutorial focado em contêineres e Kubernetes. Instale o SDK .NET 10 e crie o projeto. A rota `/api/products` retorna dados de exemplo e `/health` será usada pelas verificações de saúde do cluster. Em uma aplicação real, configure health checks que representem os critérios de prontidão e as dependências realmente necessárias.

Crie o projeto no .NET 10

dotnet new web --name Catalog.Api --framework net10.0 --no-https
cd Catalog.Api

Catalog.Api/Program.cs

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/health", () => Results.Ok(new { status = "healthy" }));

app.MapGet("/api/products", () => Results.Ok(new[]
{
    new { id = 1, name = "Keyboard", price = 79.99 },
    new { id = 2, name = "Mouse", price = 39.99 }
}));

app.Run();

Empacote a API em uma imagem de contêiner

Crie um Dockerfile multi-stage na pasta `Catalog.Api`. A etapa de build usa o SDK .NET 10; a imagem final contém o runtime ASP.NET Core e os arquivos publicados. O processo usa o usuário não root disponibilizado pela imagem oficial e escuta em HTTP na porta 8080. Em produção, mantenha a imagem identificada por uma tag imutável, como a versão do release ou o SHA do commit.

Catalog.Api/Dockerfile

FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

COPY ["Catalog.Api.csproj", "./"]
RUN dotnet restore "./Catalog.Api.csproj"
COPY . .
RUN dotnet publish "./Catalog.Api.csproj" -c Release -o /app/publish --no-restore /p:UseAppHost=false

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app
ENV ASPNETCORE_HTTP_PORTS=8080
EXPOSE 8080
USER $APP_UID
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "Catalog.Api.dll"]

Teste a imagem na sua máquina

Ainda dentro de `Catalog.Api`, faça o build e inicie o contêiner antes de enviá-lo à cloud. Assim, você consegue corrigir erros de compilação e conferir as rotas sem depender do cluster. O argumento `-p` publica a porta do contêiner no computador local.

Construa e execute localmente

docker build -t catalog-api:v1 .
docker run --rm --name catalog-api -p 8080:8080 catalog-api:v1

Em outro terminal, confira os endpoints

curl http://localhost:8080/health
curl http://localhost:8080/api/products

Para experimentar no cluster kind, carregue a imagem local com `kind load docker-image catalog-api:v1 --name dotnet-lab`, depois use `image: catalog-api:v1` em um Deployment com `imagePullPolicy: IfNotPresent`. Crie um Service `ClusterIP` e acesse-o temporariamente com `kubectl port-forward service/catalog-api 8080:80`; então teste os mesmos endpoints em `http://localhost:8080`. Essa opção evita publicar uma imagem em um registry, mas o port-forward existe apenas enquanto o comando estiver em execução e não cria um serviço público na internet.

Publique uma versão ao vivo no Azure AKS

Agora vamos criar um registry Azure Container Registry (ACR), enviar a imagem e criar um cluster AKS. Você precisará de uma conta Azure com assinatura ativa, Azure CLI atualizado e permissão para criar esses recursos. Use um resource group dedicado ao laboratório e uma região que ofereça o tamanho de VM escolhido. A imagem será construída pelo ACR a partir do Dockerfile, e a opção `--attach-acr` configura o acesso de leitura do cluster ao registry.

Instale a Azure CLI no macOS com Homebrew e entre na sua conta

brew install azure-cli
az login
az account set --subscription "SUA-SUBSCRIPTION"

RESOURCE_GROUP=rg-k8s-dotnet-demo
LOCATION=eastus
ACR_NAME=k8sdemoregistry12345
AKS_NAME=aks-dotnet-demo

az group create --name "$RESOURCE_GROUP" --location "$LOCATION"
az acr create --resource-group "$RESOURCE_GROUP" --name "$ACR_NAME" --sku Basic

# Execute na pasta Catalog.Api, onde estão o Dockerfile e o .csproj.
az acr build --registry "$ACR_NAME" --image catalog-api:v1 .

O nome do ACR precisa ser único globalmente e conter apenas letras minúsculas e números; troque o exemplo por um nome disponível. Confirme também que a assinatura selecionada é a correta e que os custos são aceitáveis. O ACR executa o build na cloud e publica a imagem versionada como `catalog-api:v1`.

Crie um cluster de laboratório e configure o kubectl

az aks create \
  --resource-group "$RESOURCE_GROUP" \
  --name "$AKS_NAME" \
  --location "$LOCATION" \
  --tier free \
  --node-count 1 \
  --node-vm-size Standard_D2s_v5 \
  --generate-ssh-keys \
  --attach-acr "$ACR_NAME"

az aks get-credentials --resource-group "$RESOURCE_GROUP" --name "$AKS_NAME"
kubectl config current-context
kubectl get nodes

A criação do cluster pode levar vários minutos, e região, quota, disponibilidade e preço do SKU variam. O nível Free do control plane não elimina a cobrança dos nós, do registry, do balanceador, do armazenamento ou do tráfego. Este cluster de nó único é apenas uma demonstração e não oferece a tolerância a falhas de produção; confirme as opções disponíveis na sua assinatura antes de executá-lo.

Configure Deployment e Service

Crie `k8s.yaml` na pasta do projeto `Catalog.Api`. Substitua `k8sdemoregistry12345` pelo nome real do seu ACR. O Deployment pede duas réplicas e define limites e solicitações de recursos; as probes verificam `/health`. O Service do tipo `LoadBalancer` solicita um endereço público Azure para o teste ao vivo. Em produção, prefira um Ingress ou Gateway com TLS e controles apropriados, e avalie rede privada quando não precisar de acesso público.

k8s.yaml

apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-api
spec:
  replicas: 2
  selector:
    matchLabels:
      app: catalog-api
  template:
    metadata:
      labels:
        app: catalog-api
    spec:
      containers:
        - name: catalog-api
          image: k8sdemoregistry12345.azurecr.io/catalog-api:v1
          ports:
            - name: http
              containerPort: 8080
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 256Mi
          readinessProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /health
              port: http
            periodSeconds: 10
---
apiVersion: v1
kind: Service
metadata:
  name: catalog-api
spec:
  type: LoadBalancer
  selector:
    app: catalog-api
  ports:
    - name: http
      port: 80
      targetPort: http

Aplique o manifesto e aguarde as réplicas ficarem prontas. O endereço externo pode aparecer como `<pending>` enquanto o Azure provisiona o balanceador; aguarde e consulte novamente. Se a aplicação não iniciar, confira os eventos, o estado dos Pods e os logs. Um erro de pull de imagem normalmente indica tag incorreta ou permissão de leitura ACR; `--attach-acr` precisa ser executado com permissões Azure suficientes para criar a atribuição necessária.

Aplique a configuração e acompanhe a implantação

kubectl apply -f k8s.yaml
kubectl rollout status deployment/catalog-api
kubectl get pods
kubectl get service catalog-api --watch

Teste a API publicada

Quando `kubectl get service` mostrar um valor em `EXTERNAL-IP`, esse endereço será o ponto de entrada HTTP público do laboratório. Em outro terminal, obtenha o IP e consulte a API. Você deve receber `{"status":"healthy"}` em `/health` e uma lista JSON de produtos em `/api/products`. Se não houver resposta, confirme que o Service recebeu um IP, que os Pods estão prontos e que a porta 80 do Service aponta para a porta 8080 do contêiner.

Consulte os endpoints pelo endereço público

kubectl get service catalog-api

API_IP=$(kubectl get service catalog-api -o jsonpath='{.status.loadBalancer.ingress[0].ip}')
curl "http://$API_IP/health"
curl "http://$API_IP/api/products"

Experimente alterar `replicas` para 3 em `k8s.yaml` e aplicar novamente; `kubectl get pods --watch` mostra o controlador criando a réplica adicional. Para inspecionar a implantação, use `kubectl describe deployment catalog-api` e `kubectl logs deployment/catalog-api`. Acessar um IP HTTP público serve para o laboratório, não para uma API de produção: adicione TLS, autenticação e autorização, monitoramento, políticas de rede e limites adequados antes de expor dados ou usuários reais.

Evite cobranças depois do teste

AKS e os serviços relacionados podem gerar custos enquanto existirem, mesmo sem tráfego. Para encerrar o laboratório, confirme que o resource group é dedicado a este exercício e que não contém outros recursos que deseja manter; em seguida, exclua esse resource group no portal Azure ou use `az group delete --name "$RESOURCE_GROUP" --yes --no-wait`. Essa exclusão remove todos os recursos dentro dele, incluindo cluster e ACR, e pode levar alguns minutos para concluir. Verifique no portal que a exclusão terminou e confira o uso de recursos na assinatura.

Conclusão

Kubernetes oferece uma API declarativa e controladores para executar aplicações em contêineres com descoberta de serviços, réplicas, atualizações e verificações de saúde. Serviços como AKS, EKS e GKE reduzem parte do trabalho de operar o cluster, mas não removem a responsabilidade de construir imagens, proteger acesso, observar a aplicação e controlar custos. Comece localmente com kind ou Minikube; quando houver um caso que justifique a operação, use um serviço gerenciado. Neste tutorial, a Web API .NET 10 percorreu o ciclo completo: build de imagem, publicação no ACR, implantação no AKS e chamada dos endpoints por um endereço público temporário.
